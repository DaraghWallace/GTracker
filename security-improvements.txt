======================================================================

    [~] 1.1 [CRITICAL] Users can choose their own role
        PROGRESS (2026-11-11):
          - Server side CLOSED (no handler reads custom:userType). CDK now
            CLOSED: userType is removed from the app client's writeAttributes
            (still readable); a test checks it. Post-confirm no longer copies
            it.
          - Still to do: the frontend sign-up form must stop sending it, or
            sign-up is rejected (FE-CHANGES.txt, part 2), and the UI should read
            the groups (part 3). Move to [R] once the frontend ships.
          - Do NOT delete the customAttributes.userType entry (pool replacement,
            see 1.7).
        Where: be/lib/constructs/auth.ts (userPoolClient writeAttributes,
            customAttributes) ; fe/src/Helpers/amplify.ts (register)
        Problem: "custom:userType" is writable by the client app. Anyone calling the
                Cognito sign-up API directly (not through your UI) can set it to
                any string, including "developer". Your Lambdas then trust that
                value for admin-style actions (Exercises create/update/delete,
                coaching endpoints). The signup dropdown only hides the options in
                the UI; it enforces nothing.
        Try: Who should be allowed to write an attribute that grants privileges?
            Search: "Cognito custom attribute mutable writeAttributes privilege
            escalation", "Cognito groups vs custom attributes for authorization".
            Test it yourself: use the AWS SDK / CLI to sign up with
            custom:userType=developer and see what your API lets you do.

    [R] 1.2 [HIGH] Authorization uses two different sources of truth
        PROGRESS (2026-11-09):
          - isInGroup() in lambda/functions/auth.ts is now the single source of
            truth. It splits the comma-separated cognito:groups string and
            matches EXACTLY (tested against lookalike names). All generic
            handlers and all trainer handlers use it.
          - Remaining: post-confirm still copies custom:userType into the
            profile table (1.9), and nothing assigns anyone to the 'members'
            group (1.8). Needs cdk deploy plus a two-account test before it
            counts as done.
        Where: lambda/functions/coachClients/*.ts (trainer check),
            generic/updateItem.ts, generic/delete.ts, generic/getItem.ts
        Problem: Trainer check = "cognito:groups contains 'trainers'" OR
                custom:userType == "developer". Signup UI stores "trainer"
                (singular) in userType and nothing ever puts anyone in the
                "trainers" group. So the intended trainer path and the real check
                disagree, and the only thing that actually works is the
                spoofable attribute from 1.1. The check is also a substring match
                on a string (what would a group called "not-trainers-lol" do?).
        Try: Decide ONE source of truth for roles. Look at how groups appear in the
            token (string vs array). Search: "cognito:groups claim format API
            Gateway authorizer".

    [ ] 1.5 [MEDIUM] Email verification / sign-up abuse

    [ ] 1.6 [MEDIUM] Role changes and disabled users take effect late
        Where: Cognito tokens (groups claim) + API Gateway Cognito authorizer
        Problem: cognito:groups lives inside the ID token. Removing someone
                from 'trainers' or 'admins', or disabling their account, does
                nothing until their existing token expires (default 1 hour)
                and any authorizer cache expires. A trainer you just removed
                keeps trainer access for up to an hour, and a refresh token
                keeps minting new tokens until it is revoked.
        Try: Search: 'Cognito token revocation', 'AdminUserGlobalSignOut',
            'Cognito token validity'. Decide on a shorter ID-token lifetime
            and use global sign-out when you revoke a role.

    [ ] 1.7 [MEDIUM] Some pool settings can't be changed later without replacing the pool
        Where: be/lib/constructs/auth.ts
        Problem: signInCaseSensitive defaults to TRUE in CDK, so Dave@x.com
                and dave@x.com are two different accounts (this also breaks
                email lookups, see 2.6). Custom attributes and some sign-in
                settings cannot be changed in place. With removalPolicy
                DESTROY on the pool, 'changing a setting' can mean 'deleting
                every user'.
        Try: Decide the final pool shape (signInCaseSensitive:false, the
            attributes you really need, MFA) BEFORE real users sign up, then
            set RETAIN (4.1). Search: 'CDK UserPool signInCaseSensitive',
            'Cognito schema attributes cannot be changed'.

    [ ] 1.8 [MEDIUM] No defined way to assign roles
        Where: Cognito groups members / trainers / admins (auth.ts creates
            them, nothing populates them)
        Problem: Nobody is added to 'members' (harmless, since 'not
                trainer/admin' means member), and trainers/admins can only be
                added by hand in the console. That is fine for a one-person
                app, but it is undocumented, unaudited, and the console is the
                only place a mistake can happen.
        Try: Write a short runbook (AdminAddUserToGroup CLI command, who may
            run it, require MFA for the admin account). If you ever want self-
            service, it needs an approval flow, not a signup field (ties to
            5.7).

    [~] 1.9 [MEDIUM] Post-confirmation trigger is fragile and copies unchecked data
        PROGRESS (2026-11-11):
          - Done in lambda/post-confirm/index.ts, with tests: (a) only
            PostConfirmation_ConfirmSignUp creates a profile, password resets
            are skipped (the trigger type list confirms Cognito also fires
            ConfirmForgotPassword); (b) userType is never stored, nickname is
            trimmed and capped at 50; (c) missing nickname/email no longer
            throws; also safe to run twice.
          - Still to do: (d) profile email still goes stale if the user changes
            it in Cognito; (e) delete lambda/services/UserService.ts (nothing
            imports it). Test a real password reset after deploying.
        Where: be/lambda/post-confirm/index.ts, lambda/services/UserService.ts
        Problem: (a) It never checks event.triggerSource. Cognito also fires

        Try: Return early unless triggerSource ===
            'PostConfirmation_ConfirmSignUp'; validate/trim nickname; stop
            storing userType (or store a constant); delete the duplicate file
            if unused.

    [ ] 2.11 [MEDIUM] addClient can create junk profile rows
        Where: lambda/functions/coachClients/addClient.ts
        Problem: UpdateItem creates the item if it does not exist, and
                'attribute_not_exists(currentTrainerId)' is true for a missing
                item. Any trainer can create a row in GtUserProfiles for any
                made-up clientId string (also with no length limit).
                removeClient is fine because its condition requires an
                existing trainer id.
        Try: Add attribute_exists(userId) to the ConditionExpression (AND-ed
            with the existing condition), cap the clientId length, and add a
            test: 'unknown clientId -> 409/404, nothing created'.

    [R] 2.12 [HIGH] Client-chosen sessionId lets one user plant data in another user's session (bypasses 2.2)
        PROGRESS (2026-11-11):
          - Done: POST /sessions now goes to createSession.ts, which makes the
            sessionId itself and ignores sessionId/userId/dateDone from the
            body. getBySession looks the session up with the full key (someone
            else's session is 404) and returns only rows the caller owns. The
            trainer handlers use findSessionById (two rows with one id -> 409)
            and getClientSessionExercises returns only the session owner's rows.
            Tests cover two users sharing a sessionId.
          - Still to do: ship the frontend change (FE-CHANGES.txt part 1)
            together with the backend, deploy, run the two-account test.
            Sessions already in the table are fine: only NEW duplicates were
            possible.
        Where: generic/create.ts (Sessions), sessions.ts model allows
            sessionId; getBySession.ts, getClientSessionExercises.ts,
            createSessionExerciseForClient.ts; and the ownership check in
            createSessionExercise.ts
        Problem: The Sessions table key is (sessionId, userId). The generic
                create takes sessionId from the body and stamps the CALLER's
                userId, so an attacker who learns a victim's sessionId (a
                uuid: not guessable, but not secret either; trainers and the
                UI see them) can create THEIR OWN session row with the same
                sessionId. (1) createSessionExercise then finds (sessionId,
                attacker) and passes its ownership check, so the attacker can
                write SessionExercises with the victim's sessionId, and
                getBySession returns every item on the sessionId-index, so the
                junk shows up in the victim's session. (2) getBySession,
                getClientSessionExercises and createSessionExerciseForClient
                all Query Sessions by sessionId alone with Limit 1, which
                returns whichever row has the lowest userId. If the attacker's
                row sorts first, the victim gets 403 on their own session, and
                a trainer's checks run against the wrong owner.
        Try: Make sessionId server-owned: generate it with randomUUID() in a
            Sessions-specific create (as createSessionForClient already does)
            and have the frontend use the returned id (5.6). Also look
            sessions up with the FULL key (sessionId + the expected userId)
            instead of Limit 1, and have SessionExercises reads return only
            rows whose userId matches the session owner. Test it: two users,
            same sessionId.
